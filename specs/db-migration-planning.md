## Role

You are a senior software architect with deep Java and Spring Boot expertise. Design (do not yet implement) an application that migrates data from a source database to a destination database while masking sensitive fields in transit. Favor the simplest design that fully satisfies every requirement below over speculative flexibility — simplicity is itself a requirement, not just a preference. Your output is a design document detailed enough that a separate implementation session can build the system from it without needing you to re-derive any decisions — but you are not writing code in this pass.

## Objective

Design a **database-agnostic, AI-assisted, one-time/batch data migration and masking tool**, built as a Java + Spring Boot application. Given connection details for a source and destination database, its default behavior is a single run that connects to both, determines the destination schema and masking plan, applies strictly one-way masking to sensitive columns, preserves referential integrity across tables, creates any missing destination schema objects, and upserts the result into the destination — all in one pass, for any supported source/destination combination, without code changes per database pair, and without any human interaction required at any stage. An optional mode allows stopping after the schema/masking plan is determined so a human can review it before data is loaded (see requirement 11).

## Functional Requirements

1. **Universal source support** — the source can be any database type, relational or non-relational (e.g., PostgreSQL, MySQL, Oracle, SQL Server, MongoDB, etc.). If full non-relational support meaningfully changes the architecture, say so explicitly in Assumptions & Open Questions rather than narrowing this requirement.
2. **Universal destination support** — same range of types as source, independently chosen.
3. **Heterogeneous pairs** — source and destination types are not required to match (e.g., Oracle → PostgreSQL, MySQL → MongoDB).
4. **No code change per combination** — adding a new supported database, or a new source/destination pairing, must be a matter of configuration or dropping in a connector plugin, not editing core logic. Design for this explicitly: what is the connector abstraction, and what contract must a new connector satisfy?
5. **Sensitive data masking, strictly one-way** — configurable masking of designated columns/fields, scoped to data covered by **GDPR, HIPAA, and PCI-DSS**. Every masking technique used must be non-reversible: no vault, no decryption key, and no lookup table that maps a masked value back to its original value — not even accessible internally by the application or an administrator. This rules out reversible tokenization-with-vault and standard (reversible) format-preserving encryption. Deterministic keyed hashing (e.g., HMAC with a secret key) is acceptable — it's one-way even though it's deterministic — alongside redaction, generalization/bucketing, and non-reversible synthetic substitution. For each technique, state which regulatory concept it satisfies (e.g., GDPR's distinction between *anonymization*, which is irreversible and takes data out of GDPR's scope, and *pseudonymization*, which is reversible and does not; HIPAA's Safe Harbor de-identification method; PCI-DSS's requirement to render PAN unreadable), and flag any residual risk (e.g., a keyed hash on a low-entropy field like a date of birth can still be brute-forced offline even though it can't be "decrypted" — note whether generalization or truncation is needed on top of hashing for such fields).
6. **Referential integrity preservation** — foreign key relationships must remain valid after masking: if a value in a parent table's primary key is masked, every child table's foreign key referencing it must be masked to the *same* resulting value, and load order must respect FK dependencies. Composite keys and self-referencing (recursive) FKs must be handled. The same deterministic one-way hashing used for requirement 5 is the natural mechanism here — confirm this and specify how the dependency graph is built and topologically sorted for load order.
7. **Batch migration with upsert re-run semantics** — this is a one-time (or periodically re-run) point-in-time migration, not continuous replication/CDC. Each table has a configured **natural key**; because masking is deterministic, a given source row always produces the same masked values across runs, so re-running a migration must **upsert/merge into the destination by natural key** (insert new rows, update changed ones) rather than truncate-and-reload or insert-only. Specify how the natural key is declared in config and how it's used to generate the upsert/merge statement per destination engine.
8. **Schema/type mapping across engines** — source and destination may use different type systems (e.g., Oracle NUMBER vs. Postgres NUMERIC vs. MySQL DECIMAL). Define how type mapping is resolved generically (a type-mapping matrix/config, not hardcoded per pair).
9. **Destination schema creation, additive-only** — the application creates missing tables and columns at the destination automatically, derived from the source schema and the type mapping in requirement 8. Destination DDL ownership is **additive-only**: the app may `CREATE TABLE IF NOT EXISTS` and `ADD COLUMN`, but must never drop, rename, retype, or otherwise alter an existing destination object, and must never delete destination data outside the normal upsert flow. Specify how the app detects "missing" vs. "already present but different" and what it does in the latter case (it must not silently alter — flag it instead).
10. **Best-effort, per-table consistency** — the application does not need to guarantee a single atomic, cross-table transaction for an entire migration run. Each table's load should be internally consistent (e.g., wrapped in its own transaction or checkpointed chunk-by-chunk), but it is acceptable for a run to leave the destination with some tables updated and others not yet reached (e.g., if the run fails partway). Specify what "consistency" means at the per-table level and how a failed/partial run is safely resumed or re-run without violating requirement 7's upsert semantics.
11. **Single run by default; optional review-before-load mode** — the default and primary way to run the application is one invocation, start to finish: connect to source and destination, determine the destination schema and masking plan (reusing a previously generated plan if the source schema hasn't changed since it was last analyzed, otherwise triggering the AI analysis from AI Usage below), then proceed straight through to masking and loading data — no human interaction required at any point. In addition, support an optional mode (e.g., a `--plan-only`/dry-run flag) that stops the run after the schema and masking plan is determined and outputs the proposed destination tables/columns and their masking assignments for human review, without loading any data; a separate, subsequent invocation then proceeds to load using that same plan (which by then is cached, so it isn't re-derived). This review step is opt-in only — never inserted automatically, and never required.
12. **Simplicity constraint** — the simplest design that satisfies requirements 1–11 wins. Prefer a single deployable Spring Boot application over a distributed or microservices architecture unless a specific requirement above genuinely forces the added complexity; avoid speculative extensibility (e.g., don't build a general plugin marketplace when a Java interface plus Spring bean registration will do).

## Technology Stack (Fixed — Java + Spring Boot)

The implementation language and framework are fixed: **Java and Spring Boot**. Do not propose alternative languages or frameworks. Within that stack you may compare a small number of sub-approaches where it matters (e.g., Spring Batch's chunk-oriented processing with restart/skip support vs. a simpler hand-rolled JDBC batch loop) and recommend one — per the simplicity constraint, default to the simpler option unless a requirement above (e.g., resumability in requirement 10, or upsert semantics in requirement 7) concretely justifies the extra machinery.

## AI Usage — Automated, One-Time, Cost-Efficient Analysis (No Human Review Gate)

AI's role is limited to schema/masking analysis, triggered only when needed within the normal run described in requirement 11 above (the default single run, or a `--plan-only` run) — never on every migration, and never as part of actual migration or masking execution. By default it does not wait on human approval — there is no required review/sign-off step between AI output and that output being used to proceed with loading data.

- **What AI does**: analyzes source schema metadata and small data samples to (a) classify which columns are sensitive within GDPR/HIPAA/PCI-DSS scope, (b) select a masking technique per sensitive column from the one-way palette in requirement 5, and (c) suggest per-table natural keys and, when source/destination schemas differ, field mappings.
- **When it runs**: as part of the same invocation, but only when there's no valid cached plan for the current source schema — i.e., the first run against a given schema, or any run after the schema has changed. If a valid cached plan already exists, that run skips AI entirely and goes straight to masking/loading (or, in `--plan-only` mode, straight to displaying the existing plan).
- **What it produces**: the analysis writes its output directly into a plan/config that the same run then consumes to proceed with loading (default mode) or displays for review and stops (`--plan-only` mode); nothing gates that output on a human decision unless `--plan-only` was explicitly requested.
- **Safety net despite no human gate**: misclassifying a sensitive column as non-sensitive is a real compliance risk with no human there to catch it. Specify a fallback policy for low-confidence AI output — e.g., default to masking when confidence is below a threshold, and/or back AI classification with a second, independent signal such as deterministic pattern rules (regex/heuristics for common PII shapes) rather than trusting AI's judgment alone.
- **Cost efficiency**: because analysis runs once per schema — not per row, not per run — state the expected cost driver explicitly (e.g., "~1 call per table or per N columns during analysis, independent of row count and migration frequency") and how the design keeps it that way at 10, 100, and 1000+ table schemas.
- **Actual migration and masking execution is entirely AI-free**: once config exists, runtime masking is deterministic, rule-based Java code driven entirely by that config — no AI dependency and no network call to an AI provider at run time.

Produce a design document with the following sections, in this order:

1. **Assumptions & Open Questions** — list anything you're assuming due to ambiguity in this brief, and flag decisions that need a human answer before implementation.
2. **High-Level Architecture** — major components/services (as Spring beans/modules within the single deployable app) and how data flows between them, described precisely enough to be turned into a diagram (name each component, its responsibility, and its inputs/outputs).
3. **Connector Abstraction** — the interface/contract every source and destination connector must implement: schema introspection, read/extract, upsert/write, type-mapping hooks, and additive-only DDL generation (create missing tables/columns; detect but never resolve "present but different" cases automatically). 4. **Masking Engine Design** — the one-way masking techniques supported (per requirement 5), how a column is mapped to a technique in config, how determinism is guaranteed for FK-referenced columns, how the regulatory framing (GDPR/HIPAA/PCI-DSS) maps to technique choice, and the masking config schema (show an example).
5. **Referential Integrity Strategy** — dependency graph construction from FK metadata, load ordering, handling of composite/self-referencing/cross-schema keys, and what happens when FK metadata is missing or unreliable (e.g., in databases with no enforced constraints).
6. **AI Integration Points (Triggered Only When Needed, No Required Human Gate)** — exactly where within a run AI is invoked (first run against a schema, or after a schema change — never when a cached plan is already valid), what it's given as input (schema metadata vs. data samples — specify which and how much), what it returns, the automated fallback/safety-net policy for low-confidence classifications, and confirmation that no AI call occurs during actual masking/loading. Include the cost/scalability justification from the section above.
7. **Data Flow for a Run** — step-by-step sequence from job start to completion for both the default single run and the optional `--plan-only` run: schema/masking plan determination (reusing a cached plan or triggering AI analysis), destination schema reconciliation (additive DDL), and then — for the default run only — extraction batching/chunking for large tables, per-table masking, upsert-by-natural-key load respecting FK order, per-table consistency handling (best-effort, per requirement 10), error handling, and resumability if a run fails partway. Specify exactly where `--plan-only` stops and what it outputs for review.
8. **Java/Spring Boot Architecture Mapping** — concrete choices: relevant Spring Boot starters/modules, the batch-processing approach chosen above, how connector plugins are registered (e.g., a Java interface plus Spring bean discovery), config binding (e.g., `@ConfigurationProperties` over YAML), connection pooling, the run entrypoint (e.g., `CommandLineRunner`), and how the HMAC secret/key used for masking is managed and kept out of source control and logs.
9. **Configuration Schema** — two related shapes: (a) the minimal input a user provides up front (source/destination connection details, and any overrides they want to force rather than leave to AI analysis) and (b) the generated/cached plan produced by schema+masking analysis (table/column selection, per-column masking technique, per-table natural key, type-mapping decisions, DDL actions to take) that a run consumes directly, and that `--plan-only` mode outputs for review. Entirely declarative either way, with no runtime-interactive parameters. Show a concrete example of each.
10. **Non-Functional Considerations** — credential/secrets handling (including the masking key), audit logging of what was masked and how, performance/parallelism strategy, failure/resume behavior consistent with best-effort per-table consistency, a testing/validation strategy (how correctness of masking, referential integrity, and additive-only DDL gets verified), and what audit evidence the design produces to support GDPR/HIPAA/PCI-DSS compliance reviews.
11. **Handoff Spec for Implementation** — for every core component identified in section 2 (connectors, masking engine, referential-integrity resolver, DDL generator, upsert/natural-key writer, orchestrator including the default vs. `--plan-only` run modes, and the AI-assisted plan generator), list its key Java interfaces/classes/methods (signatures, not bodies) and the config or data structures they consume/produce, at a level of detail sufficient for a separate implementation session to build against without re-deriving these decisions. Design the whole system in its final, complete form — do not phase or stage the implementation plan itself.
12. **Implementation Task List** — a flat, dependency-ordered list of concrete implementation tasks derived directly from section 11, sized for an AI coding agent to pick up and execute one at a time (e.g., "implement the `SourceConnector` interface and the Postgres adapter," "implement the FK dependency graph builder and topological sort," "implement the HMAC-based one-way masking strategy," "implement the additive-only DDL generator," "implement the upsert-by-natural-key writer," plus the plan/config model classes, orchestrator wiring for both run modes, and the tests for each). Order strictly by dependency, not by calendar phase or MVP-vs-later staging — this is a single implementation effort, not a roadmap. Each task should name the file(s)/class(es) it produces and which other tasks it depends on.
